1. Shells

What is a shell, really?

Think of it like this: the shell is a translator standing between you and the Linux kernel. You speak in commands like ls or mkdir, and the shell translates that into instructions the machine actually understands.

  • A terminal is just a window. The shell is the program running inside it doing the real work
  • You can type commands one at a time (interactive mode), or write a whole list of them in a file and run them together (a script)
  • A shell script is not scary. It's a plain text file with a list of commands, run from top to bottom
In the real worldThe moment you SSH into a server on AWS, DigitalOcean or any cloud host, a shell is the first thing that greets you. Get comfortable here and servers stop feeling intimidating.

1. Shells

Check your current and available shells

Picture this: first day at a new job, you SSH into a server you've never touched before. Before typing anything else, check what shell you're standing in.

$ echo $SHELL              # shell set for your user account
/bin/bash

$ ps -p $$                 # shell actually running THIS session
  PID TTY    TIME CMD
 3312 pts/0  00:00:00 bash

$ cat /etc/shells          # every shell installed on the system
/bin/sh
/bin/bash
/usr/bin/zsh

$SHELL can be stale after switching. ps -p $$ is the live, trustworthy check.

1. Shells

Change your shell

Temporary, just for this session

$ zsh          # just launch it; type 'exit' to return

Permanent, your default login shell

$ chsh -s /usr/bin/zsh     # set a new default (may ask for your password)
$ chsh -s /bin/bash         # switch back to bash any time

Some teams prefer zsh for its autocomplete and themes. Knowing how to switch means you're never stuck with a default you didn't choose. All examples from here use Bash, the shell you'll meet by default on almost every Linux server on earth.

2. Bash Basics

Your first script

This is the moment you stop being someone who just uses Linux and become someone who builds with it. Every script starts with a shebang, telling Linux exactly which interpreter should run it:

#!/bin/bash
echo "Hello, Linux World!"
  1. Save it as hello.sh
  2. Make it executable: chmod +x hello.sh
  3. Run it: ./hello.sh (or bash hello.sh without chmod)
Try it nowOpen a terminal and type those three lines yourself. Right now, before the next slide. It takes thirty seconds and it's the best way to make this actually stick.
3. Static Scripts

Static programs: no variables needed

Say every morning you SSH into a server just to check the date, the disk space and who else is logged in. Three commands, every single day. A static script runs all three for you in one shot, no thinking required.

#!/bin/bash
# systeminfo.sh — always runs the same fixed commands
echo "Today's date:"
date
echo "Disk usage:"
df -h
echo "Who else is logged in:"
who
In the real worldSysadmins call this a health check script. It never changes its behavior. It just saves you from typing the same commands forever.
3. Static Scripts

Predefined variables

Bash quietly keeps track of useful information for you. You never declare these, they're just there when you need them.

Environment variables

$HOMEyour home folder
$USERcurrent username
$PWDcurrent directory
$PATHexecutable search path

Special script variables

$0script name
$1..$9positional arguments
$#number of arguments
$?exit status of last command
#!/bin/bash
# run as: ./backup.sh /var/www
echo "Script $0 was run by $USER"
echo "Backing up folder: $1"
echo "You passed $# argument(s)"
4. Variables

User-defined variables

#!/bin/bash
name="Alice"          # no spaces around the =
age=25                # no $ when you assign it
echo "Hello, $name, you are $age years old"
  • Use $name to read a variable. No $ when you assign it
  • Quote variables when you use them: "$name" avoids weird, hard to spot bugs
  • readonly price=10 locks a value so nothing can change it later
  • unset name removes a variable completely

This is the same idea a website uses to show "Welcome back, Sarah." Same concept, way simpler under the hood.

5. Dynamic Scripts

Dynamic programs: talking to your user

A dynamic script reacts to whoever is running it, using read to capture whatever they type.

#!/bin/bash
read -p "What's your name? " name
echo "Nice to meet you, $name!"

read -p "Which website should I check? " site
echo "Checking $site now..."

Arguments typed at launch, like ./script.sh Alice, make a script dynamic too. Read them with $1, $2 and so on.

5. Dynamic Scripts

Arithmetic operations

read -p "Hours worked: " hours
read -p "Hourly rate: " rate

echo "You earned $((hours * rate)) this week"
echo "Remainder if split 3 ways: $((hours % 3))"

The double parentheses $(( )) are the modern, preferred way to do math in Bash. You'll also spot let and expr in older scripts doing the same job.

Bash only handles whole numbers natively. For decimals, pipe into bc: echo "3.5+2" | bc

6. Conditionals

If statements

Picture a server slowly filling up its disk. Nobody notices until it's too late and the site goes down. An if statement is how a script notices for you, before that happens.

if [ $usage -ge 90 ]; then
    echo "Critical: disk almost full"
elif [ $usage -ge 70 ]; then
    echo "Warning: keep an eye on this"
else
    echo "All good"
fi
NumbersStringsFiles
-eq -ne= !=-f is file
-gt -lt-z empty-d is directory
-ge -le-n not empty-e exists
6. Conditionals

If, in action

#!/bin/bash
# even_odd.sh
read -p "Enter a number: " num
if [ $((num % 2)) -eq 0 ]; then
    echo "$num is even"
else
    echo "$num is odd"
fi
#!/bin/bash
# disk_check.sh
read -p "Enter current disk usage %: " usage
if [ $usage -ge 90 ]; then
    echo "Send an alert now"
elif [ $usage -ge 70 ]; then
    echo "Log a warning"
else
    echo "Nothing to do"
fi

This exact pattern, check a number then react, is most of what real monitoring scripts do in production.

6. Conditionals

Case statements

When you're matching one value against several options, case reads far cleaner than a long chain of if/elif.

#!/bin/bash
# app_control.sh
read -p "start, stop or status? " action
case $action in
    start)  echo "Starting application..." ;;
    stop)   echo "Stopping application..." ;;
    status) echo "Checking status..." ;;
    *)      echo "I don't recognize: $action" ;;
esac

This is basically a tiny version of what tools like systemctl do under the hood. *) catches anything unexpected, just like else.

7. Loops

For loops

# list form
for fruit in apple mango kiwi
do
    echo "I like $fruit"
done
# range form
for i in {1..5}
do
    echo "Server check #$i"
done
# C-style form
for (( i=0; i<5; i++ ))
do
    echo "i = $i"
done

Swap "apple mango kiwi" for a real list of servers or usernames, and this stops being a toy example and becomes actual admin work.

7. Loops

While, until and loop control

# while: run WHILE true
count=1
while [ $count -le 5 ]
do
    echo "Attempt $count"
    ((count++))
done
# until: run UNTIL true
count=1
until [ $count -gt 5 ]
do
    echo "Attempt $count"
    ((count++))
done

break exits a loop early. continue skips straight to the next round.

Real-world remixThis exact shape is how deployment scripts wait for a server to come online: until ping -c1 google.com &> /dev/null; do echo "Waiting for network..."; sleep 2; done
7. Loops

Functions, your shortcut

#!/bin/bash
log() {
    local message=$1
    echo "$(date): $message"
}

log "Backup started"
log "Backup finished"

Copy-pasting the same three lines into ten different scripts is a maintenance headache waiting to happen. Define it once, call it by name, and every script you write from now on stays short and readable.

8. Cron

Automating scripts: cron jobs

This is how Netflix, your bank and pretty much every server on the internet runs jobs at 3 AM without a single human clicking a button. Meet cron, the scheduler quietly running Linux systems since 1975.

*  *  *  *  *  command_to_run
│  │  │  │  │
│  │  │  │  └── day of week (0-6, Sun=0)
│  │  │  └───── month (1-12)
│  │  └──────── day of month (1-31)
│  └─────────── hour (0-23)
└────────────── minute (0-59)

Example: 0 2 * * * /home/user/backup.sh runs at exactly 2:00 AM, every single day, forever.

Shortcuts exist too: @reboot, @daily, @weekly, @monthly.

8. Cron

Managing your crontab

$ crontab -e   # edit your personal crontab
$ crontab -l   # list your scheduled jobs
$ crontab -r   # remove all jobs, careful with this one

Put it together

0 2 * * *     /home/user/backup.sh >> /var/log/backup.log 2>&1
*/15 * * * *  /home/user/check_disk.sh
0 9 * * 1-5   /home/user/daily_report.sh

Write a script once, then let cron run it every night while you sleep. That backup line above genuinely runs on real servers right now, at companies you've heard of.

Wrap-up

Habits that separate hobbyists from pros

  • Always start with #!/bin/bash and comment your intent
  • Quote your variables: "$var" avoids weird, hard to spot bugs
  • set -x prints every command as it runs, priceless for debugging
  • set -e stops your script the moment something fails
  • Run your script through ShellCheck before you trust it
  • Use exit codes on purpose: exit 0 means success, anything else means something broke

These aren't nitpicky rules. They're the difference between "it works on my machine" and a script your whole team actually trusts in production.
