Task 1 · Step 1

Install Apache2 and prepare the website directory

Goal: Install the web server and create a directory for the site files. Run these commands on VM1.
sudo apt update
sudo apt install apache2 openssl -y
sudo systemctl enable --now apache2
systemctl is-active apache2
sudo mkdir -p /var/www/29061.f26
sudo chown -R "$USER":www-data /var/www/29061.f26
sudo chmod -R 755 /var/www/29061.f26

What this does: apt update refreshes package information. Apache2 serves HTTP requests; OpenSSL creates and inspects the certificate. enable --now starts Apache now and enables it at boot. The directory stores website content. The owner can edit files while Apache's group can read them.

Expected result: systemctl is-active apache2 prints active.

Task 1 · Step 2

Configure the HTTP virtual host and local domain

Goal: Tell Apache which domain maps to the website directory.
sudo nano /etc/apache2/sites-available/29061.f26.conf

Add these key lines:

<VirtualHost *:80>
    ServerName 29061.f26
    DocumentRoot /var/www/29061.f26

    ErrorLog ${APACHE_LOG_DIR}/29061.f26-error.log
    CustomLog ${APACHE_LOG_DIR}/29061.f26-access.log combined
</VirtualHost>

Explanation: *:80 listens for HTTP on port 80. ServerName selects the domain; DocumentRoot identifies the folder Apache serves. The log directives keep this site's errors and access records separate.

sudo a2ensite 29061.f26.conf
sudo apache2ctl configtest
sudo systemctl reload apache2
Expected result: the configuration test prints Syntax OK.

Make the domain resolve on each test device

The domain 29061.f26 is a project/local name, not automatically a public DNS name. Add the VM1 IP and domain to the hosts file on VM1 and on any device where you want to type the domain.

sudo nano /etc/hosts
# Add one line, replacing VM1_IP with VM1's actual LAN IP:
VM1_IP  29061.f26

On Windows, edit C:\\Windows\\System32\\drivers\\etc\\hosts as Administrator and add the same mapping. If the second device cannot edit hosts, test by IP instead. A hosts entry changes name resolution only on that device.

Task 1 · Step 3

Generate and verify a self-signed TLS certificate

Goal: Create a certificate whose Subject Alternative Name matches 29061.f26.
sudo openssl req -x509 -nodes -days 365 \\
  -newkey rsa:2048 \\
  -keyout /etc/ssl/private/29061.f26.key \\
  -out /etc/ssl/certs/29061.f26.crt \\
  -subj "/O=AUCA/OU=Linux-F26/CN=29061" \\
  -addext "subjectAltName=DNS:29061.f26"
sudo chmod 600 /etc/ssl/private/29061.f26.key

Explanation: req -x509 creates a self-signed certificate; -newkey rsa:2048 creates a new 2048-bit RSA key; -nodes leaves the key unencrypted so Apache can start without an interactive passphrase; -days 365 sets validity; -subj fills certificate identity fields; -addext adds the DNS name used for hostname verification. The private key is restricted to its owner.

Inspect the certificate

sudo openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -subject -issuer -dates
sudo openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -ext subjectAltName
sudo openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -text

For a self-signed certificate, the issuer and subject are normally the same. Check that the SAN output contains DNS:29061.f26 and that the dates cover the current time. Self-signed means browsers do not trust it automatically; for this class project, curl -k can test the HTTPS connection while skipping trust verification.

Task 1 · Step 4

Enable Apache SSL and create the HTTPS virtual host

Goal: Configure Apache to serve the same site over HTTPS on port 443.
sudo a2enmod ssl
sudo nano /etc/apache2/sites-available/29061.f26-ssl.conf

Use this virtual-host configuration:

<VirtualHost *:443>
    ServerName 29061.f26
    DocumentRoot /var/www/29061.f26

    SSLEngine on
    SSLCertificateFile /etc/ssl/certs/29061.f26.crt
    SSLCertificateKeyFile /etc/ssl/private/29061.f26.key

    ErrorLog ${APACHE_LOG_DIR}/29061.f26-ssl-error.log
    CustomLog ${APACHE_LOG_DIR}/29061.f26-ssl-access.log combined
</VirtualHost>

Explanation: SSLEngine on enables TLS for this virtual host. The certificate and private-key directives point to the files generated in the previous step.

sudo a2ensite 29061.f26-ssl.conf
sudo apache2ctl configtest
sudo systemctl restart apache2
sudo systemctl reload apache2
sudo apache2ctl -S

Use apache2ctl -S to inspect which virtual hosts Apache has loaded. If the default site catches HTTP requests, inspect /etc/apache2/sites-enabled/ and disable only the conflicting default configuration if appropriate.

Task 2 · Overview

Automate system reports and backup delivery

The example flow is: VM1 creates a report, compresses it into a ZIP file, and transfers the ZIP to VM2. VM2 watches its incoming directory and emails a notification when a new ZIP arrives.

VM1

Collect system information → create ZIP → transfer to VM2.

VM2

Receive ZIP → detect new file → send email alert → host documentation with NGINX.

Task 2 · Step 1

Check networking and set up SSH key authentication

Goal: Make sure VM1 can reach VM2 and authenticate without entering the account password for each transfer.

Run on both VMs to inspect addresses:

ip -br address
ip route
ping -c 4 192.168.56.101

Replace the example address with VM2's reachable IP. A failed ping alone does not prove SSH is broken because ICMP may be blocked. Test SSH itself as well.

On VM2, install and start the SSH server if needed:

sudo apt update
sudo apt install openssh-server -y
sudo systemctl enable --now ssh
systemctl is-active ssh
sudo ufw allow OpenSSH

On VM1, create an Ed25519 key if you do not already have a suitable key:

ls -la ~/.ssh
ssh-keygen -t ed25519 -C "vm1-to-vm2"
ssh-copy-id mutangana@192.168.56.101
ssh mutangana@192.168.56.101

Accept the first-connection host-key prompt only after checking that the destination is the intended VM. Enter the VM2 account password during ssh-copy-id if prompted; later SSH logins should use the installed public key. Never copy the private key (usually a file without .pub) to VM2.

If you generated a custom key filename, such as ~/.ssh/vm2_key, use ssh-copy-id -i ~/.ssh/vm2_key.pub mutangana@192.168.56.101 and make the transfer script use ssh -i ~/.ssh/vm2_key or configure an SSH alias.
Task 2 · Step 2

Create the system report script on VM1

Goal: Collect the student ID, timestamp, hostname, logged-in users, disk status, and uptime, then package the report.
mkdir -p ~/bin ~/outgoing
nano ~/bin/create_report.sh

Use this complete example. It keeps temporary report files in a dedicated directory and sends the ZIP to ~/outgoing.

#!/bin/bash
set -euo pipefail

id="29061"
timestamp="$(date +%Y%m%d_%H%M%S)"
hostname="$(hostname)"
workdir="$HOME/report-work"
outgoing="$HOME/outgoing"
report="${id}_${timestamp}.txt"
zip_file="${id}_${timestamp}.zip"

mkdir -p "$workdir" "$outgoing"
cd "$workdir"

{
    echo "Student ID: $id"
    echo "Report created: $(date '+%Y-%m-%d %H:%M:%S')"
    echo "Host: $hostname"
    echo
    echo "==== Logged-in Users ===="
    who
    echo
    echo "==== Disk status ===="
    df -h
    echo
    echo "==== System uptime ===="
    uptime
} > "$report"

zip -q "$zip_file" "$report"
mv "$zip_file" "$outgoing/"
rm "$report"

echo "Created: $outgoing/$zip_file"

Explanation: set -euo pipefail makes the script stop on common errors. The timestamp gives each report a unique name. The braces group report commands and redirect their output to the text file. zip compresses it; mv places the ZIP in the outgoing folder; rm removes the uncompressed temporary report.

chmod +x ~/bin/create_report.sh
~/bin/create_report.sh
ls -lh ~/outgoing
Expected result: a timestamped 29061_....zip file appears in ~/outgoing.
Task 2 · Step 3

Transfer the backup and schedule it with cron

Goal: Send the generated ZIP files from VM1 to VM2 and automate the process.

First create VM2's receiving directory using the VM1 SSH account:

ssh mutangana@192.168.56.101 'mkdir -p ~/incoming'

Create the transfer script on VM1:

nano ~/bin/transfer_reports.sh
#!/bin/bash
set -euo pipefail

REMOTE_USER="mutangana"
REMOTE_HOST="192.168.56.101"
REMOTE_DIR="incoming"
OUTGOING="$HOME/outgoing"

mkdir -p "$OUTGOING"

# Copy ZIP reports to VM2. -p preserves timestamps; -v shows copied files.
find "$OUTGOING" -maxdepth 1 -type f -name '*.zip' -print0 |
while IFS= read -r -d '' file; do
    scp -p "$file" "${REMOTE_USER}@${REMOTE_HOST}:${REMOTE_DIR}/"
    # Move delivered files to an archive folder to avoid sending them repeatedly.
    mkdir -p "$OUTGOING/sent"
    mv "$file" "$OUTGOING/sent/"
done

Explanation: find selects ZIP reports only. Null-delimited filenames safely handle spaces. scp copies each ZIP to VM2's incoming directory. Successfully transferred files are moved into outgoing/sent so later runs do not repeatedly upload them. Keep the SSH key and destination account correctly configured.

chmod +x ~/bin/transfer_reports.sh
~/bin/create_report.sh
~/bin/transfer_reports.sh

After confirming manual transfer works, schedule the jobs on VM1. Open the current user's crontab:

crontab -e

Example: create a report and transfer files every 5 minutes. Use separate lines so the transfer runs after report creation in the same cron invocation:

*/5 * * * * /home/mutangana/bin/create_report.sh >> /home/mutangana/backup-cron.log 2>&1 && /home/mutangana/bin/transfer_reports.sh >> /home/mutangana/backup-cron.log 2>&1

Replace /home/mutangana with the actual home directory for the account whose crontab you edited. Cron has a minimal environment, so use absolute paths and log output. Check the scheduled entry with crontab -l and inspect ~/backup-cron.log.

Scheduling note: This example runs both commands every five minutes. If your assignment requires a different schedule, change the five-minute expression to the required interval.
Task 2 · Step 4

Configure VM2 to detect incoming backups and email a notification

Goal: Monitor VM2's incoming folder and send an email when a new file has finished arriving or has been moved into the folder.

Run on VM2:

sudo apt update
sudo apt install inotify-tools msmtp-mta bsd-mailx zip -y
inotifywait --version
msmtp --version
dpkg -s bsd-mailx | grep '^Status:'

Package roles: inotify-tools provides filesystem event monitoring; msmtp-mta sends mail through an SMTP server; bsd-mailx provides the mail command; zip creates compressed report archives on VM1.

Configure msmtp without publishing secrets

nano ~/.msmtprc

Example structure only—replace the example addresses and add your app password locally. Do not paste the real password into this website, screenshots, or a public repository.

defaults
auth on
tls on
tls_starttls on
tls_trust_file /etc/ssl/certs/ca-certificates.crt
logfile ~/.msmtp.log

account gmail
host smtp.gmail.com
port 587
from sender@example.com
user sender@example.com
password YOUR_APP_PASSWORD_GOES_HERE

account default : gmail
chmod 600 ~/.msmtprc
printf 'This is a mail test from VM2.\n' | mail -s "VM2 Email Test" receiver@example.com

Use an app password where the provider requires one; normal account passwords may not work. Protect the configuration because it contains credentials. The real value must stay on VM2 and must be replaced with a placeholder in the documentation.

Create the file-monitor script on VM2

mkdir -p ~/incoming ~/bin
nano ~/bin/watch_incoming.sh
#!/bin/bash
set -u

INCOMING="$HOME/incoming"
RECEIVER="receiver@example.com"
SOURCE="VM1"

mkdir -p "$INCOMING"

inotifywait --monitor \
  --event close_write \
  --event moved_to \
  --format '%f' "$INCOMING" |
while read -r FILENAME; do
    TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"
    printf 'New backup received.\nFilename: %s\nSource: %s\nReceived at: %s\n' \\
      "$FILENAME" "$SOURCE" "$TIMESTAMP" |
      mail -s "New Backup Received: $FILENAME" "$RECEIVER"
done

Explanation: --monitor keeps watching. close_write reports a file whose writing has finished; moved_to detects a file moved into the directory, such as an SCP upload finalized by rename. --format '%f' outputs only the filename. read -r reads it without treating backslashes as escapes. The timestamp is calculated inside the loop so each email gets the time of its own event.

chmod +x ~/bin/watch_incoming.sh
~/bin/watch_incoming.sh

Leave the script running while testing. For a persistent service, configure a systemd user/service unit or another supervisor; a terminal session closing will stop this foreground script.

Task 3 · Step 3

Create and enable the NGINX server block

Goal: Tell NGINX to serve the documentation directory.
sudo nano /etc/nginx/sites-available/29061-docs

Use these key configuration lines:

server {
    listen 80;
    listen [::]:80;
    server_name _;

    root /var/www/29061-docs;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

Explanation: listen 80 accepts HTTP connections on port 80; server_name _ acts as a catch-all for this IP-based project site; root points to the documentation folder; index identifies the default page; try_files serves the requested file or returns 404 if it does not exist.

sudo ln -s /etc/nginx/sites-available/29061-docs /etc/nginx/sites-enabled/29061-docs
ls -l /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

If the default NGINX site conflicts, disable it only after checking the active configuration:

sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

Removing that symlink disables the default site; it does not delete the original file in sites-available.
