Task 1 · Step 1

Install Apache2 and OpenSSL on VM1

Goal: Install the web server and OpenSSL tools used to create and inspect the certificate.
sudo apt update
sudo apt install openssl
sudo apt install apache2

Alternatively, run the installation in one command:

sudo apt update && sudo apt install apache2 openssl -y

apt update refreshes the package index. Apache2 serves web pages, while OpenSSL creates and checks the self-signed TLS certificate.

Check the Apache2 service

Expected result: The service status reports that Apache2 is active and running.
Task 1 · Step 2

Create the website directory and HTTP virtual host

Goal: Tell Apache which directory to serve for the local project domain.

The website files are stored in:

/var/www/29061.f26

Create it if it does not already exist:

sudo mkdir -p /var/www/29061.f26

Open the HTTP virtual-host file:

sudo nano /etc/apache2/sites-available/29061.f26.conf

Configuration used:

<VirtualHost *:80>
    ServerName 29061.f26
    DocumentRoot /var/www/29061.f26

    ErrorLog ${APACHE_LOG_DIR}/29061.f26-error.log
    CustomLog ${APACHE_LOG_DIR}/29061.f26-access.log combined
</VirtualHost>

Explanation: *:80 listens for HTTP traffic on port 80. ServerName selects the local domain, and DocumentRoot points to the website folder. The final directives configure separate error and access logs.

Enable and validate the configuration

sudo a2ensite 29061.f26.conf
sudo apache2ctl configtest
sudo systemctl reload apache2
Expected result: apache2ctl configtest prints Syntax OK.

Configure the local domain

Because 29061.f26 is a project domain, add a hosts-file entry on each device that needs to resolve it. The entry maps VM1's actual IP address to the domain:

sudo nano /etc/hosts

# Add a line using VM1's actual IP:
VM1_IP  29061.f26

On Windows, edit C:\Windows\System32\drivers\etc\hosts as Administrator. The placeholder VM1_IP must be replaced with the IP of VM1; it is not a literal address.

Task 1 · Step 3

Generate and verify the self-signed certificate

Goal: Generate a certificate for 29061.f26 and verify its identity and validity.
sudo openssl req -x509 -nodes -days 365 \
  -newkey rsa:2048 \
  -keyout /etc/ssl/private/29061.f26.key \
  -out /etc/ssl/certs/29061.f26.crt \
  -subj "/O=AUCA/OU=Linux-F26/CN=29061" \
  -addext "subjectAltName=DNS:29061.f26"

What the options mean:

  • -x509 creates a self-signed X.509 certificate.
  • -nodes creates an unencrypted private key so the server can start without an interactive key passphrase.
  • -days 365 sets the certificate validity period.
  • -newkey rsa:2048 creates a 2048-bit RSA key.
  • -keyout and -out set the private-key and certificate paths.
  • -subj provides the certificate subject fields.
  • -addext adds the Subject Alternative Name (SAN), which contains the DNS name.

Restrict access to the private key:

sudo chmod 600 /etc/ssl/private/29061.f26.key

Inspect the certificate

openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -subject -issuer -dates
openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -ext subjectAltName
openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -text

These commands show the certificate subject, issuer, validity dates, SAN, and full certificate details. Check that the SAN contains DNS:29061.f26. Because the certificate is self-signed, browsers do not automatically trust it.

Check the certificate served by Apache and compare public keys

echo | openssl s_client -connect 29061.f26:443 -servername 29061.f26 2>/dev/null | openssl x509 -noout -subject -dates
openssl x509 -in /etc/ssl/certs/29061.f26.crt -noout -pubkey | openssl sha256
sudo openssl pkey -in /etc/ssl/private/29061.f26.key -pubout | openssl sha256

The first command inspects the certificate returned by the HTTPS server. The next two calculate SHA-256 hashes of the certificate's public key and the public key derived from the private key. Matching hashes confirm that the certificate and private key belong together.

Task 1 · Step 4

Enable SSL and configure the HTTPS virtual host

Goal: Enable Apache's SSL module and configure the site to use port 443.

Enable SSL and restart Apache2:

sudo a2enmod ssl
sudo systemctl restart apache2
sudo systemctl reload apache2

Create the HTTPS virtual-host file:

sudo nano /etc/apache2/sites-available/29061.f26-ssl.conf

Configuration used:

<VirtualHost *:443>
    ServerName 29061.f26
    DocumentRoot /var/www/29061.f26

    SSLEngine on
    SSLCertificateFile /etc/ssl/certs/29061.f26.crt
    SSLCertificateKeyFile /etc/ssl/private/29061.f26.key

    ErrorLog ${APACHE_LOG_DIR}/29061.f26-ssl-error.log
    CustomLog ${APACHE_LOG_DIR}/29061.f26-ssl-access.log combined
</VirtualHost>

Explanation: This virtual host listens on HTTPS port 443. SSLEngine on enables TLS, and the certificate directives point to the certificate and private key generated in the previous step.

Enable and validate HTTPS

sudo a2ensite 29061.f26-ssl.conf
sudo apache2ctl configtest
Expected result: Syntax OK.

Reload the service to apply the virtual-host configuration:

sudo systemctl reload apache2
Task 1 · Step 5

Configure the firewall and test HTTP/HTTPS

Goal: Allow web traffic and test the website locally and from another device.

Allow HTTP and HTTPS through UFW:

sudo ufw allow 443/tcp

Task 2 · Step 2

Create the system report with report.sh

Goal: Record the student ID, timestamp, hostname, logged-in users, disk status, and system uptime in a text report, then zip it into an outgoing folder.

The report script you supplied is shown below. Save it as report.sh in the location you use on VM1.

#!/bin/bash

id=29061
timestamp="$(date +%Y%m%d_%H%M%S)"
hostname="$(hostname)"
file="${id}_${timestamp}.txt"
zip_file="${id}_${timestamp}.zip"
OUTGOING="$HOME/outgoing"

echo >> "$file"
echo "Student ID: $id" >> "$file"
echo "Report create: $(date '+%Y-%m-%d %H:%M:%S')" >> "$file"
echo "Host: $hostname" >> "$file"



echo  >> "$file"
echo ==== Logged-in Users==== >> "$file"
echo >> "$file"
who >> "$file"
echo >> "$file"

echo >> "$file"
echo ==== Disk status ==== >> "$file"
echo >> "$file"
df -h >> "$file"
echo >> "$file"

echo >> "$file"
echo ==== System uptime ==== >> "$file"
echo "$file"
uptime >> "$file"
echo >> "$file"

zip "$zip_file" "$file"
rm "$file"

mv "$zip_file"  "$OUTGOING"

How it works: The timestamp makes the report and ZIP filenames unique. hostname records the machine name, who lists logged-in users, df -h shows disk usage, and uptime shows how long the system has been running. zip compresses the report, rm removes the text file, and mv moves the ZIP to the outgoing folder.

Check before running: Make sure $HOME/outgoing exists. The line echo "$file" prints the filename to the terminal instead of adding it to the report; it is preserved here as it appeared in your notes. Also make sure the script's final move succeeds and the outgoing directory is writable.
mkdir -p "$HOME/outgoing"
chmod +x report.sh
./report.sh
Task 2 · Step 3

Transfer ZIP backups with send-backups.sh

Goal: Find ZIP files in the outgoing directory, transfer each file to the VM incoming directory over SCP, and move the local file to the sent directory.

The transfer script you supplied is shown below:

#!/bin/bash


OUTGOING="$HOME/outgoing"


for file in "$OUTGOING"/*.zip; do

if [[ -f "$file" ]] then

echo "Transferring: $file"
scp "$file"  29061@10.117.138.200:/home/29061/incoming/

echo "Transfer successful: $file"

mv "$file" "$HOME/sent"
else
echo "Transfer failed: $file"
fi

done

How it works: The for loop checks ZIP files in $HOME/outgoing. scp copies each selected file to /home/29061/incoming/ on the destination machine. mv then moves the local file to $HOME/sent, preventing it from being selected again in later runs.

Syntax and reliability check: In Bash, the condition line should use if [[ -f "$file" ]]; then (or put then on the following line). The version pasted above is preserved from your notes, but if it is exactly what is saved on disk, run bash -n /home/29061/scripts/send_backups.sh to check it. Also, the script currently prints “Transfer successful” without checking SCP's exit status; verify the actual file arrived before relying on that message.

The script also expects $HOME/sent to exist. Create it if necessary:

mkdir -p "$HOME/sent"
Task 2 · Step 4

Schedule the transfer with cron

Goal: Run the backup transfer script automatically every minute.

Open the crontab for the user who owns the script:

crontab -e

The cron line from your notes is:

* * * * * /home/29061/scripts/send_backups.sh >> /home/29061/logs/logfile 2>&1

Explanation: The five asterisks mean every minute, every hour, every day of the month, every month, and every day of the week. The command runs the transfer script. >> appends normal output to the log file, while 2>&1 sends error output to the same log.

Make sure the paths exist and the script is executable:

chmod +x /home/29061/scripts/send_backups.sh
mkdir -p /home/29061/logs
crontab -l
Your cron line runs send_backups.sh, not report.sh. This means report creation must be triggered separately or by another configured job for new ZIP files to appear. Keep the schedule as shown if that is the configuration you used, and verify how report creation is scheduled in your actual setup.
Task 2 · Step 5

Install the notification packages on VM2

Goal: Install the file watcher, SMTP client, mail command, and ZIP utility.
sudo apt update
sudo apt install inotify-tools msmtp-mta bsd-mailx zip -y

Verify the tools:

inotifywait --version
msmtp --version
dpkg -s bsd-mailx
  • inotifywait: watches filesystem events in a directory.
  • msmtp: sends email using an SMTP server.
  • MTA: stands for Mail Transfer Agent, software used to send or relay mail.
  • bsd-mailx: provides the command-line mail utility. BSD stands for Berkeley Software Distribution; mailx is a family/name of command-line mail utilities.
  • zip: creates ZIP archives for the system reports.

Try the file watcher

inotifywait --monitor --event close_wait --event moved_to --format %f /home/29061/incoming

This is the manual watcher command from your notes. --monitor keeps watching, --format %f prints the filename, and moved_to detects files moved into the directory.

Event name check: Standard inotifywait commonly uses close_write (a file has finished being written), rather than close_wait. Your notification script below uses close_write. If the manual command reports an invalid event, use close_write for the test.

Task 2 · Step 7

Send an email whenever a new backup arrives

Goal: Watch VM2's incoming directory and email joegithub12@gmail.com when a new file arrives.

The script from your notes:

#!/bin/bash

INCOMING="$HOME/incoming"
RECEIVER="joegithub12@gmail.com"
TIMESTAMP="$(date +'%Y-%m-%d %H:%M:%S')"
SOURCE="VM1"

inotifywait --monitor --event close_write --event moved_to --format %f "$INCOMING" |
 while read -r FILENAME; do
   echo "New file detected:\n $FILENAME"
   echo -e "New backup received.\nFilename: $FILENAME\nSource: $SOURCE\nReceived at: $TIMESTAMP\n" |
    mail -s "New Backup Received: $FILENAME" "$RECEIVER" 
 done

How it works: INCOMING points to the watched folder. RECEIVER is the notification recipient. inotifywait waits for completed writes or files moved into the directory and prints each filename. The loop reads that filename and sends a message using mail.

Timestamp note: In the script as written, TIMESTAMP is set once when the script starts, so every email will show the start time rather than the time of the new file. If you want the exact arrival time, move that assignment inside the while loop. The message's echo -e formats the newlines in the email body.

Save the script in the location you use on VM2, make it executable, and run it:

chmod +x ~/watch_incoming.sh
~/watch_incoming.sh

Keep the watcher running while testing. A file already present before the watcher starts does not create a new event for the running watcher.
